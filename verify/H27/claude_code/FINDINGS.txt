## 2. Commands [V: `source/steps.json`, `source/steps/*`]

All run from the work dir with `--output-format json --dangerously-skip-permissions`.

- **New session:** `claude -p "<prompt>"`. Stdout is a JSON result `{"type":"result","subtype":"success","session_id":…,"result":…}`.
- **Resume with a prompt:** `claude -p --resume <id> "<prompt>"`. It keeps the **same session id and appends to the same file**; T2, compact, T3 and T4 all returned c45db7bc….
- **Compaction:** `claude -p --resume <id> "/compact"`. The result text is `Compacted …`, exit 0, trigger `manual`.
- **Interrupted turn:** `claude -p --resume <id> "H27-HANG" --output-format stream-json --verbose`, process tree killed with `taskkill /T /F` after 15 s. Stdout holds only the `system/init` event.
- **Fork:** `claude -p --resume <id> --fork-session "<prompt>"`. It returns a new id (ab331b72…) and writes a new file.
- **`--resume <id>` from a different cwd works** [V: O]:
  - it finds the file in the original project folder and appends there;
  - the appended rows carry the new `cwd`;
  - an empty `projects\<new flattened cwd>\memory\` folder appears;
  - the request carries both the old environment block and `Primary working directory: …\othercwd (was …\work)`.

**Record types in S**

  - `api-request-shape`
  - `api-request-blob {hash, message}`: the system-role messages actually sent.

**Row shapes**
- **User text** (S:3): `{"parentUuid":null,"promptId":"…","type":"user","message":{"role":"user","content":"H27-TOOLS read C:\\…\\alpha.txt and C:\\…\\beta.txt"},"permissionMode":"bypassPermissions","promptSource":"sdk","turnOrigin":"sdk","turnPosition":{"promptIndex":0,"turnIndex":1},…}`. The content is a plain string.
- **One API response = one row per content block** (S:21→22→23→24):
  - all rows share the same `message.id` (`msg_h27_2`);
  - the full message envelope (`model, stop_reason:"tool_use", usage`) is repeated on each row;
  - each row also carries `apiBlockIndex` 0..3, `requestRef` (= the `api-request.id`), `requestedModel` and `effort:"medium"`;
  - the rows are chained by `parentUuid`.
- **Thinking** (S:21): `"content":[{"type":"thinking","thinking":"H27-REASONING: …","signature":"h27-mock-signature"}]`, with row fields `thinkingDurationMs` and `thinkingDisplay:"omitted"`. **The signature is stored.**
- **Assistant text** (S:22): `"content":[{"type":"text","text":"H27-PRE: reading the files."}]`.
- **Tool call** (S:23, S:24): `"content":[{"type":"tool_use","id":"toolu_h27call2x0","name":"Read","input":{"file_path":"C:\\…\\alpha.txt"}}]`.
- **Tool result** (S:25, S:26): one `user` row per result:
  `"message":{"role":"user","content":[{"tool_use_id":"toolu_h27call2x1","type":"tool_result","content":"1\tBETA-CONTENT-17"}]},"toolUseResult":{"type":"text","file":{"filePath":"…","content":"BETA-CONTENT-17","numLines":1,"startLine":1,"totalLines":1}},"sourceToolAssistantUUID":"<its tool_use row>","permissionDecision":{"decision":"accept","source":"config","reasonType":"mode"}`.
  The model sees `1\tBETA-CONTENT-17` (Read's line-numbered form); `toolUseResult` keeps the raw file content.

**Two parallel calls**
- The two tool_use rows form a chain (x0 row → x1 row).
- **Each tool_result row's `parentUuid` is its own tool_use row.** Results are written in completion order, and the turn continues from the *last written* result.
- In S the x1 result came first (S:25, parent = x1 row S:24) and x0 second (S:26, parent = x0 row S:23). S:27 hangs off S:26.
- Walking `parentUuid` back from the leaf therefore skips S:24 and S:25. In an earlier run with the other completion order, the walk skipped only the x0 result.
- The request regroups them [V: C #3]: one assistant message `[thinking, text, tool_use x0, tool_use x1]` and one user message `[tool_result x0, tool_result x1]`.
- A reader must merge rows by `message.id` and collect results by `tool_use_id` / `sourceToolAssistantUUID`.

`last-prompt.leafUuid` is written when the request starts, so it lags: S:18 points to the x1 tool_use row.

## 8. Surprises

- The role-`system` messages inside `messages` (beta `per-turn-control-2026-07-01`) broke the shared mock (§1).
- Parallel tool results branch the `parentUuid` tree (§3). The leaf walk alone loses a call or a result.
- Compaction keeps a verbatim tail by reference (`preservedSegment`) instead of rewriting rows, and it re-injects files read earlier. The summary tells the model the absolute path of the full transcript.
- The interrupted turn gets its `<synthetic>` "No response requested." reply only when the session is next loaded.
- The mock answers T3 (`H27-T3 after compaction`) with the summary text, because its `SUMMARY_RE` matches "compaction". This is the mock's behaviour, not Claude Code's.

## 9. Open problems

- Auto-compaction (by threshold) was not tried, nor was compacting a session that ends in an unanswered tool call.
- Whether the `.claude.json` onboarding and approval fields are required in `-p` mode was not isolated.
- `resume-capture.ps1` runs in the session's recorded cwd only when it lies under `%LOCALAPPDATA%\shinatama-verify`; otherwise it uses the scratch work dir, or `-Cwd` if given. A txcript-written session with a real-project cwd will therefore show an "Environment update … (was …)" block in the capture.
