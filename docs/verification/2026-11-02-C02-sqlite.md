# C02 — embedded SQLite and typed project state

Date: 2026-11-02. Windows 11 x64 build 26200. Dependencies are locked:
rusqlite 0.40.2 with bundled SQLite/FTS5. No database server or separate SQLite
installation is required by the application.

## Delivered behavior

Desktop project history now uses the private `shinatama.db` prepared in C01.
Typed commands expose projects and storage diagnostics; no generic SQL command
or database handle is available to the frontend. Disk access runs on blocking
workers. Each process has its own connection; SQLite coordinates short
`BEGIN IMMEDIATE` write transactions. No network or agent call occurs in one.

Effective pragmas are read back: `journal_mode=wal`, `synchronous=1` (NORMAL),
`foreign_keys=1`, `busy_timeout=5000`. A temporary full-text table verifies real
FTS5 insert/search behavior; no unused future schema is created. The minimal
authoritative schema is `project` and `setting`. Projects have stable `p_` plus
12 random base32-character IDs and UTC Unix-millisecond timestamps. Limiting the
visible recent list to ten never deletes older authoritative project records.

B02 `projects.json` is bounded, strictly validated and imported once, inside a
transaction coordinated with the old writer's filesystem lock. Original bytes
remain unchanged after import and subsequent SQLite selections. Missing project
paths remain represented. Invalid/future JSON cannot partially import records or
complete the import marker. Once completed, the app no longer depends on the old
JSON being valid; the database is authoritative.

A crash-released private initialization lock serializes version inspection and
schema setup. Version 1's table/index/constraint definitions are checked before
persistently changing its journal configuration. SQL normalization preserves
literal case, whitespace and escaped quotes. Unknown schemas and corrupt files
fail without automatic replacement. A future version opens read-only, displays
an update message and refuses changes. Database/WAL/SHM permissions are inspected
and secured without following reparse points or hard links.

## Remaining boundaries

C03 adds versioned verified backup/migration handling; this C02 schema is version
1. Session/thread schemas, their ownership and liveness, resource supervision,
agents, sidecar and transcript indexing are later increments. Native agent stores
are not imported or modified by this step. The old B02 binary must not be used
as an authoritative writer after migration: its source JSON remains recoverable,
but selections made there after the import are not automatically replayed.

`npm run test:state` passed against the real embedded executable, through the P14
test wrapper: three native app launches, JSON import and unchanged source bytes,
selection through the UI, stable IDs and restored choice, restart despite a
subsequently corrupted legacy JSON, and schema 999 opened read-only with an update
message. The future database's bytes and rows remained unchanged after close.
No terminal was started automatically and neither synthetic project was modified.

Transient initialization failures currently require closing and reopening the app
after their cause is fixed; the once-per-process service does not silently replay
failed startup operations. Full interactive recovery follows the later service
and resilience increments.
