# C03M.2/C03M.3 — desktop maintenance qualification

Date: 2026-11-02. Status: local Windows qualification passed.
The durable machine-readable record is
[C03M-desktop.result.json](2026-11-02-C03M-desktop.result.json).

The desktop owns one optional maintenance worker, with a real 60-second tick and
30 seconds of inactivity required before automatic work. Input hints contain no
key text, are throttled, and revoke pending optional work. A manual check reserves
the worker before entering the blocking pool; repeated requests cannot create an
unbounded queue. Reservation registers its cancellation token immediately, so a
pressure pulse or activity before execution remains effective. Clearing pressure
does not replay the revoked batch.

The worker uses the library's dedicated connection and process-wide file/lease
coordination. It never initializes storage just to run maintenance. Drop cancels
and signals the worker without joining a possibly blocked native call on the UI.
The initial host admission requires 1 GiB available commit and 512 MiB available
physical memory. This is a conservative admission check, not C09R's calibrated
adaptive governor; `inhibit_optional_work` is the integration point for that step.

Integrity failures, malformed operational metadata, anomalous records and capacity
deferrals produce a visible, deduplicated explanation. A capacity deferral is
visible even when the database itself is below its size warning: low disk space
and excessive WAL can also prevent admission. Saved records remain unchanged.

The real desktop proof uses synthetic state and an actual PowerShell ConPTY. It
checks repeated manual jobs, concurrent requests, writer contention and recovery,
the unchanged automatic idle interval, bounded metadata, sensitive-payload
exclusion, integrity and authoritative-row hashes. Terminal marker age and UI
round-trip measurements have explicit thresholds. The real idle run passed:
218 samples, UI round-trip p95 16 ms / maximum 488 ms; screen marker age p95
1,008 ms / maximum 1,508 ms; largest observed marker-advance gap 1,510 ms.
These measure UI IPC and rendered output, not full keystroke-to-shell latency.
The unchanged scheduler ran about 56.6 seconds after the last input (its first
60-second tick starts at app setup). Six explicit checks completed; a burst of
16 requests returned in 63 ms during writer contention. Recovery succeeded.
Operational metadata ended at two rows / 420 bytes with one aggregated anomaly.
The artifact's outcome counts are report observations, including repeated status
reads, rather than a count of distinct executed jobs.

The initial driver incorrectly read the entire accessibility container: xterm's
later DOM announcement region deliberately retains older output after its line
limit. Reading the current screen-row tree fixed that measurement error; the
2,000 ms age, 3,000 ms advance-gap and 1,500 ms UI thresholds were unchanged.
The final test and P14 wrapper both exited zero, and all owned processes closed.

The integrated Rust suite passed **113 tests** (including 91 state-library tests
and eight desktop-controller/bridge tests), with Clippy warnings denied and
formatting clean. Frontend build / three tests, 29 Python checks, dependency

The core's separate fixtures cover a real crashed owner process, lock exclusion,
finite lease recovery, future schemas, cancellation/pressure, reduced capacity
budgets, malformed records, interrupted SQL and repeated bounded batches. Reduced
capacity is fault injection; the test never fills the host's disk or memory.

The integrated suite also reproduced a real concurrent-startup failure: SQLite
can remove WAL/SHM between an existence probe and the private-file inspection.
Windows may expose that deletion as NotFound, a briefly denied open, or a handle
with zero links. The database now inspects optional sidecars directly. Transient
open errors have at most 100 ms of retry waiting; persistent denial still fails.
Zero links is treated as deletion only when
[`FileStandardInfo`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_standard_info)
on that same handle confirms `DeletePending`. The main database, parent ownership, reparse
points and actual multiple hard links retain strict checks. Native regressions
cover pending deletion, persistent denial, absence without recreation and hard
link refusal; the concurrent import fixture performs eight independent rounds.
This is startup race recovery, not a relaxed permission policy.

Reproduction, serially after building the current embedded desktop executable:

```powershell
cargo test --offline --workspace --all-targets --features custom-protocol -j1 -- --test-threads=1
cargo clippy --offline --workspace --all-targets --features custom-protocol -j1 -- -D warnings
verify/P14/target/debug/p14-probe.exe wrap-run node apps/desktop/tests/maintenance-smoke.mjs
```

The P14 wrapper confines the test's owned processes. Production P14 containment
and the wider C09R resource/fault matrix remain open. Native filesystem I/O and
SQLite checkpoint I/O have no hard preemption guarantee; the SQL VM budget is
cooperative and does not promise a 100 ms end-to-end job.
