# SC16 soak verification - 2026-11-13

Scope: local transport latency of the pinned sidecar while five concurrent clients keep
long, growing histories moving through it. This is the **short run (120 s)**. The
one-hour run is pending and is recorded in its own section below.

## What was run

- Shinatama revision at run time: `d39d6b5070580220c4328ebdaa1f11094eb09ed3` (branch
  `bc-stabilization`, with the soak test and the shared harness uncommitted in the
  working tree at the time of the run).
- Pin fingerprint: `entrySha256` `99137457918384b9288ada4d23de24632779944759be3f33c7421cc2805dde0a`
  (`sidecar/source-build/provenance.lock.json`, package version 0.1.207; the pin carries the
  per-session retrieve export).
- Test: `five_instances_for_one_hour_refuse_no_connection` in
  [`crates/engine/tests/sidecar_soak.rs`](../../crates/engine/tests/sidecar_soak.rs),
  on the harness in `crates/engine/tests/support/sidecar_harness.rs` shared with the SC9 and
  isolation proofs. The sidecar is started through the real owner supervisor with the
  product's per-stream output cap (64 MiB). Its only upstream is the synthetic local origin
  (`crates/engine/tests/fixtures/origin.mjs`, started with `--no-record`); no provider is
  contacted.
- Load: 5 concurrent clients, each on its own session. Each client resends its whole history
  every turn; the history grows to 150,000 estimated tokens (four bytes per token), and a
  tool result of 5,000 to 6,800 tokens (above the 4,000-token CCR threshold) enters every
  third turn. At the cap a client opens a new session. The origin holds each reply stream
  open for 3,000 ms before it ends (`SHINATAMA_SOAK_STREAM_MS`, default 3000), as a model
  generating a turn would.
- A sixth client, every 250 ms, measures a `CONNECT` to a loopback echo target through the
  sidecar (TCP connect, tunnel set-up and the 12-byte echo round trip) and `GET /__bili/health`.
- Command: `SHINATAMA_SOAK_SECONDS=120 cargo test -p shinatama-engine --test sidecar_soak -- --ignored --nocapture --test-threads=1`
- Result file: `target/sc16-soak.json`.

`longestHoldMs` is the longest time one of the five clients waited for a complete reply, so
it includes the origin's 3,000 ms stream. `refusedConnections` counts TCP connections the
sidecar did not accept, and `CONNECT` requests it did not answer with 200, for all six
clients. The test also requires every other request to succeed (status 200 and the origin's
reply) and the sidecar to report no request in flight after the clients stop.

Other 120 s runs with the same load and no change in between:

| Run | connectMsMax | healthMsMax | longestHoldMs | Verdict |
|---|---|---|---|---|
| 1 | 118.7 | 26.0 | 3152.3 | pass |
| 2 | 2230.4 | 30.5 | 5381.7 | fail: one `CONNECT` plus echo of 2.2 s, p95 27.0 |
| 3 | 147.8 | 23.9 | 3148.5 | pass |
| 4 | 1376.2 | - | 3175.0 | fail: one probe of 1.4 s at +63 s (possibly overlapped with another native run on the same machine) |
| 5 (above) | 114.9 | 37.2 | 3127.7 | pass |

In runs 2 and 4 one probe took longer than the 750 ms bound while the other samples stayed at
the p50 and p95 above. Health was served in time immediately afterwards, so the stall was
brief and its cause is not established here. Two of five short runs therefore did not meet
the bound; the one-hour run will expose the same behaviour many times over. The cause belongs
to the open SC16 profiling item (longest hold and its cause), not to this record.

Saturation stress, not the SC16 load: with the origin ending each stream at once
(`SHINATAMA_SOAK_STREAM_MS=0`) the five clients send back to back. Over 120 s the sidecar
handled 468 requests with `connectMsP50` 2011.0, `connectMsP95` 2163.8, `connectMsMax` 2171.9,
`healthMsMax` 2047.8, `longestHoldMs` 2203.3 and 964153 stderr bytes, no refused connection.
The sidecar process used about one core continuously, so its single event loop is the limit:
five clients resending histories of this size need more than it can serve without delaying a
tunnel. This is recorded as a capacity finding, not as a failure of the soak above.

## What this proof does not cover

- The sidecar's internal event-loop delay. `monitorEventLoopDelay` runs inside the sidecar
  engine; this proof observes latency only from outside, through `CONNECT` plus echo and
  health. The register item keeps asking for it.
- Traffic to real providers. The origin is synthetic and local, answers with one fixed reply
  and never rate-limits, validates or slows a request the way a provider does.
- Other operating systems: the proof is Windows only.
- The cause of the occasional one-probe stall above.
