# harness/cli survey: architecture, past problems, lessons for Shinatama

Date: 2026-10-28. Question: "look at harness/cli more deeply: how it is structured architecturally, which problems they found in the past and how they solved them."
Method: read-only inspection of a full clone of `github.com/harness/cli` (Go, Apache-2.0; 463 commits, 49 tags, latest v3.10.1 on 2026-10-22), its 268 PRs and 99 issues through `gh` (about 130 bodies read), release notes, and the predecessor repository `harness/harness-cli`. Nothing from the clone was built or run. References are PR/issue numbers on harness/cli; dates are 2026 unless stated. "(inference)" marks a conclusion no source states.

Why it matters: harness/cli is not a coding-agent harness. It is Harness.io's platform CLI, but its stated first consumer is AI agents, and it makes a heterogeneous surface (modules owned by different teams, one plugin binary) uniform under one grammar. Shinatama does the same job one level up, for the harnesses it hosts.

## 1. Architecture

A table-driven interpreter. 17 embedded spec files (`pkg/spec/*.spec.yaml`, about 17.9k lines, 594 commands) are parsed at every start into a `Registry`, validated, and turned into a Cobra tree. About 517 commands are `handler_type: endpoint` (one declared HTTP call plus expr-lang projections) and about 78 are `workflow` (named Go functions). Everything that varies per API lives in data; everything uniform (grammar, auth, scope, paging, formats, confirmation, completion, telemetry) lives once in `pkg/registry`. A plugin is the same framework built as another binary; the host only routes to it.

```
main ─► specloader.LoadSpecs ─► Registry ◄─ ModuleInit registers Go hooks "module:id"
        embedded specs + ~/.harness/spec/*.yaml (installed plugins)
  └► BuildCommands ─► cobra <verb> ─► <noun[:variant]> ─► bindHandler
        ├─ External: plugin.Exec(harness-x)   (execve on Unix, child + exit code on Windows)
        ├─ Endpoint: buildCtx → CallEndpoint (+ paging strategy)
        └─ Workflow: Go fn(ctx)
                     ▼
        format.Format{Array,Single}Output (exprenv: it/ctx/auth/flags + helpers)
        stdout = data only │ stderr = errors, spinners, notices
```

- **YAML to Go boundary.** YAML reaches Go only through string ids in about 12 hook slots (`workflow_id` 78, `body_fn` 16, `text_formatter` 15, `fetch_fn` 10…), namespaced `module:id` (`moduleregistrar.go:17-21`). `task check:specs` runs the built binary with `HARNESS_CHECKSPECS=1` and fails if a referenced hook is unregistered (`rootcmd.go:72-89`). In production, unknown YAML keys are tolerated (`registry.go:77`). Example: `update project` (`platform.spec.yaml:660-679`) is pure data (`PUT` path, `update_strategy: get-then-put`, pick/wrap expressions, field types); the whole platform module (48 commands) has one Go hook.
- **Plugins** (since #106). Install writes `~/.harness/bin/harness-<name>` and captures its grammar by running `<bin> --spec` into `~/.harness/spec/<name>.spec.yaml` with a host-owned provenance block; "Core is the only writer of spec files" (`install_plugin.go:135-141`). Identity gate: `--identity` must print `{"harness_plugin_name", version, build_time}` matching the file name (`pkg/plugin/identity.go:107-139`). Staged write then rename "so a concurrent dispatch never sees a half-written binary"; archive entries flattened to base names. Loading treats specs as untrusted: 1 MiB cap, no symlinks, `module_core` forbidden, whole-spec conflict check before registration so "a plugin can never override a builtin" (`registry.go:295-345`); a bad plugin spec is a warning. Across the exec boundary only argv and environment pass; the plugin re-parses with the same registry code and re-resolves auth from the same files. The real contract is the shared Go library (`modules/har/go.mod` uses `replace => ../../`). Version compatibility is thin: a `spec_version` range check, no minimum host version; `HARNESS_PLUGIN` is set for "the plugin-side self-check" (`registry.go:897-899`) but nothing reads it.
- **Output.** stdout carries data only. ANSI helpers turn on only when `IsPty && !isMachineFormat` (`exprenv.go:20-27`). JSON gets an injected `url`. `--list-columns`/`--list-fields` print the schema without calling the API; hidden `--preview-request` builds the request without sending. Four paging strategies behind one interface (`pkg/endpoint/pagingstrategy.go:22-46`); item output has no paging envelope, agents are told "fewer items than requested → you've reached the end" (`docs/paging.md`). Agent detection feeds telemetry only. Gap: lists default to `table` even when stdout is not a terminal, despite the comment at `format.go:55` saying "table only when attached to a terminal".
- **Auth.** Order: `--profile`, `HARNESS_PROFILE`, `HARNESS_API_KEY`, `default` profile; naming a profile ignores every auth environment variable ("no blending"). Pipeline mode turns on only for commands whose spec declares it, fixes the scope, and evaluates headers in an environment holding only the token "so other spec expressions can't read the pipeline token" (`exprenv.go:191-194`). Metadata and tokens in separate 0600 files; no "active profile" field.
- **Verb rules** (`docs/verb-variants.md`: "The grammar shape must tell the agent the truth before dispatch"). Cost order reuse > `noun:variant` > new noun > new verb; a variant is its own entry, so an impossible combination is never registered instead of failing at run time; "the id identifies the noun"; update vs execute decided by "is there a call that puts this back?"; no negation flags; blast radius in the first token. Delete needs the id typed, or `--force` without a TTY (`confirm.go:26-34`).
- **Cross-cutting.** Background update check at most every 24h, the same binary re-invoked with a sentinel flag; "Update checking must never break normal commands" (`release.go:59-80`). Telemetry records an intent event before execution, flag names only, never values. 131 test files next to the code, no golden files, policy "test the module, not the framework". CODEOWNERS splits core from modules; a core feature and its adoption go in separate PRs.
- **Docs vs code.** At least nine disagreements, among them: `docs/plugins.md` describes the pre-#106 model (`external_binary`, lookup on `PATH`); the promise of help and completion for uninstalled plugins is false (they answer "provided by the "har" plugin, which isn't installed", `registry.go:608`); the verb set is not six (push, pull, configure, install, migrate exist; `audit`/`validate` documented but absent); `paging.md` says `--all` overrides `--offset`, the code errors; `auth.md` examples use the old noun-first grammar; the confirmation gate tests stdout but its error says "stdin is not a terminal" (`confirm.go:34`).

## 2. History: before "3.0"

- **Generation 1, `harness`** (harness/harness-cli, 2023-05-30, tags v0.0.x): resource-YAML files, CD and GitOps.
- **Generation 2, `hc`** (same repo, v1.0.0 on 2025-11-11, still shipping v1.3.47 on 2026-10-01): `hc <command> <subcommand>`, Artifact Registry plus a raw `api` passthrough; its README says it "will be deprecated soon".
- **Harness MCP server** (harness/mcp-server, 2025-05-14) was the earlier channel for agents. `docs/verbs.md:389` deletes six verbs as "leftovers from the MCP migration"; issue #369 (10-28) tests the CLI "as the default tool for coding agents (instead of the Harness MCP)".
- **3.0**: squashed from a private repository (292 commits) on 06-05, renamed to harness/cli on 07-13; tags jumped from v0.1.21 to v3.0.0 on 07-14. The only stated reasons are positioning: one grammar, spec-driven, self-describing, agent-first (`docs/verb-arch.md`: "predictability over discoverability"). No document compares 3.0 with `hc`.

## 3. Problems and how they were solved (ranked)

1. **YAML-declared commands shipped broken.** Commands were declared but never run against the API: empty path segments → 405 on `create pr` (#37), `--set` rejected (#23), PATCH paired with get-then-put silently sent as POST (#64), whole modules aimed at wrong API paths (#43, #67, #111, #198).
   Fix: mutation engine rebuilt (#253–#256, 09-29) with a hidden `--preview-request` that prints the write instead of sending it; core vs module PR split with CODEOWNERS (#277). Held only partly: #28 (`--set` rejects every field on many nouns, open since 06-22), #370.
2. **Auth: four modes and their precedence.** Profile, env var, SSO, pipeline. Service-account login failed with 403 until validation moved to a token-validate endpoint (#70). Flipped precedence so `HARNESS_PROFILE` beats `HARNESS_API_KEY`, and the reserved names `env`/`pipeline` hard-error instead of "silently falling through" (#281, 10-09; flagged as breaking in #280). `--org`/`--project` ignored in env mode (#317–#321). Proxies: a raw TCP dial ignored them (#300), Go silently drops an unparseable proxy variable and connects directly (fixed by failing loudly, #301), SSO skipped the proxy check (#310), one module built transports without `Proxy` and worked "only by accident" (#156/#160). Windows SSO opened the browser with `cmd /c start`; replaced in v3.6.2 (#181). Declined: rejecting a non-0600 credentials file (#18), because containers and pipelines break.
3. **Plugin distribution and version skew.** Plugin framework (#106, 08-11): plugins in `~/.harness/bin`, one spec each in `~/.harness/spec`, an `--identity` check on install, the plugin released on its own tags, and the old bundled archive still produced "so already-installed clients on the prior self-update path don't break". Follow-ups: `go:embed` could not see specs from another repository, so plugins now supply their own spec bytes (#112, #123); commands of an absent plugin now name the plugin to install (#108); the host translates aliases because plugins know only canonical names (#133); `install cli` runs the *new* binary's own `install plugin all` "so plugin-install changes ship with the release that introduces them" (#145). Skew remains: har v1.1.1 had to be rebuilt on core v3.10.1 to get a gateway fix.
4. **Install, upgrade, renames, Windows.** Two mass renames in two months (repository rename with an 11-day download fallback; Go `/v3` module path, 176 files, #189). Self-update refuses a binary outside the install directory and a Homebrew-owned one without `--force`; it writes `.new` then renames. Windows "couldn't be packaged, installed, or self-updated" until #71 (08-03), two months after launch; CI still runs on Ubuntu only. WSL behind corporate TLS inspection breaks `curl | sh` (#61), answered with a manual-install document.
5. **Porting from the legacy `hc` while it kept shipping.** Gaps surfaced in waves (#76, #207/#233, #240, #259, #288, nine issues #332–#342): failed migrations exited 0, `--dry-run` actually uploaded for five package types, an unlocked shared result list under-reported. Fix: vendored the four OpenAPI specs and generated clients instead of hand-written HTTP (#236). Open: `configure` overwrites npm/pip/maven/nuget configs without a backup (#338, #342).
6. **Grammar and verbs.** Agents with `gh` habits typed `harness pr create`; the CLI now prints the corrected command and exits non-zero, "no silent auto-rewrite" (#41). Six never-used verbs deleted; recorded lesson (`docs/verbs.md:396`): "mint a verb when its first occupant arrives, not in anticipation. An unoccupied verb is worse than an absent one". Flags that apply only sometimes were turned into noun variants (`configure registry:npm`, #164/#171), called "the single biggest source of malformed agent invocations" (`docs/verb-variants.md`).
7. **Output and docs for agents.** `--format csv` on `get` silently returned JSON; the fix was to reject the flag (#3). `--all`/`--count` without a total now error (#15). A `url` field in JSON so tools stop building URLs (#62/#81). Docs misled agents: AGENTS.md "misled another agent" (#273); #369 (open) lists flags documented but absent (`-y`, `--since`). "Claude Code has no reason to look for a `harness` binary" (#274, open).
8. **Process.** About 30 commits carry `AI-Tool: claude-code` trailers; a review bot posts advisory grammar reviews; four commits pushed straight to main were reverted the same day and re-landed through a PR. Release notes are empty from v3.0.0 to v3.7.1.
9. **Telemetry and agent detection.** `pkg/telemetry/agent.go` reads environment markers (`CLAUDECODE=1`, `CODEX_SANDBOX`, `OPENCODE_CLIENT=1`, `CURSOR_AGENT`, `/opt/.devin`). Events no longer batched in a short-lived process; a placeholder id until the first interactive run so containers do not create users. The opt-out (`HARNESS_NO_TELEMETRY`) exists only in code, in no document.
10. **TUI.** Key collisions between built-in scroll keys and spec-defined bindings (#169); `--ui` ignores `--limit`/`--offset` (open).

## 4. Lessons for Shinatama

Mine, to check. Each one names the Shinatama part it touches.

1. **Adapters (functional design §6): declare capabilities as data, code only through named hooks, and fail the build when a hook is missing.** Their problem 1 shows the cost of the opposite: declarations that were never run against the real target. Each adapter capability (export, import, resume, handover, needs input, turn finished) needs a conformance test that drives the real harness, not a test of the framework.
2. **Version gate per hosted harness: already designed** (`fixture_gate(version) -> Supported | Degraded | Unsupported`, technical design 5.5). harness/cli confirms the need: it has no minimum-version field, and its own plugin had to be rebuilt to get a core fix. The same holds for the hop preview, already designed as the single source of what the destination receives (technical design §1 item 4); their `--dry-run` that really uploaded (#240) shows why it must be one choke point.
3. **Installing harnesses and Daodan: identity check, staged write plus rename, never touch a package-manager-owned install, and let the new version run its own post-install step** (#106, #145, Homebrew guard). Daodan already ships compiled per harness; Shinatama only installs it, and these are the install mechanics.
4. **Environment hygiene when starting a harness: one documented precedence, explicit selectors that hard-error, no silent fall-through** (#281, #301). Concrete case found today: this shell has `CLAUDECODE=1` inherited from the session it runs in, and Claude Code 2.1.312 treats `CLAUDECODE`/`CLAUDE_CODE_CHILD_SESSION` as "child session" and strips them itself for its children. Shinatama should remove these markers before starting a hosted harness, by exact name and never by prefix (`CLAUDE_CODE_*` would also delete user settings such as `CLAUDE_CODE_USE_BEDROCK`). **Adopted 2026-10-28:** technical design §3 and adapter contract 5.5 A, register P20. Proxies must reach every HTTP path, sign-in included (#300, #310).
5. **Windows in CI from day one.** Their Windows support came two months late (#71), its bugs after release (#181), and `cmd /c start` was replaced for SSO (#181). Shinatama targets macOS, Linux and Windows (functional design §3, ConPTY still unproved), so CI should run on all three before the first adapter lands.
6. **If Shinatama exposes commands to the hosted agents (hop, roundtable, task state): their grammar rules apply as written.** Mint a verb when its first command arrives; variants instead of flags that apply only sometimes; suggest the corrected command and exit non-zero, never rewrite silently; stdout data only; generate help and the agent skill from the registry. Their most persistent defect is docs promising commands and flags that do not exist (#273, #369, nine drifts in §1); generated docs avoid it. The skill would ship as a Daodan plugin, so Daodan's compiler carries it to every harness.
