# FS03 — authoritative root and workspace records

2026-11-02, Windows local verification passed: **115 state tests**, Clippy with
warnings denied, formatting, dependency inventory and frontend/desktop builds.
The real embedded app passed three restarts, legacy import with stable project IDs,
schema-3 persistence and byte-preserving read-only refusal of schema 999. The C11
real UI/CLI convergence proof also passed on the updated app.

Schema 3 adds only the currently required `store_root` and `workspace` records.
The existing verified-backup migration protocol remains mandatory before v2→v3.
Tests preserve old project/setting rows and uncheckpointed WAL, validate the v2
backup, roll back injected failure after new DDL, retry safely and reopen without
repeating a completed migration. A fresh database has three verified snapshots.
No actual user database was migrated by these tests.

Root bindings retain canonical path, origin, revision, primary/additional scope
and access. Additional roots are system/read-only in SQL and typed validation.
A primary is unique within agent/kind/configuration revision. Reconnection appends
a new identity with a unique predecessor; concurrent successors and scope escalation
refuse. Removing a root marks it unavailable without deleting bindings or history.
Native references include root ID and revision, so equal native IDs remain distinct.

Workspace writes use a revision CAS and one window owner with PID plus exact OS
creation fingerprint. Saved JSON is bounded to 256 KiB and excludes known runtime
payload fields. Restoration returns data only. Unknown layouts remain untouched;
tree validation, previous valid layouts and actual UI ownership recovery belong to
C06. All new writers recheck schema inside `BEGIN IMMEDIATE`; an already-open writer
refuses every mutator after another connection advances the database to version 999.

Authoritative/operational classification does not grant cleanup authority. Current
records remain protected by C03M; future operational tables and their rebuild/retention
jobs are introduced and qualified with their owning features. No empty future
tables or generic table-dropping/rebuild API were added.
